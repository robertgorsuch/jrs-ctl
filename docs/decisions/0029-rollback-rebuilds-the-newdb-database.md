# ADR-0029: Rollback of a newdb run rebuilds the database from the point-B export, and only samedb asks for a backup

Status: accepted, 2026-09-18. Supersedes ADR-0012 for `--mode newdb`; ADR-0012 stands for `samedb`.

## Context

ADR-0012 established what `js-upgrade-newdb` does: it drops the repository database named in `default_master.properties`, recreates it with the target schema and imports the point-B full export into it. Because jrsctl could not undo that, both modes were gated behind `--db-backup-confirmed`, and `upgrade rollback` restored files only: webapp, buildomatic, configuration, keystore. After a failed newdb run the old webapp therefore came back against a database that no longer matched it, and the plan told the operator to restore the database from their own backup or to re-import the point-B export by hand.

The second field test of v1.6.0 (`docs/reviews/2026-09-18-field-test-2-review.md`, second round) called that out twice. "Rollback is also questionable": a rollback that leaves the server unable to start is not one. And "the tool is asking before the upgrade whether you've done the backup or not and then does the backup of its own, which seems redundant": for newdb, jrsctl's own full export *is* the repository backup, taken with the service stopped so nothing changes after it (ADR-0025), and asking for another one before taking it reads as the tool not trusting its own work.

What the vendor tooling offers was checked on the 10.0.0 buildomatic on this machine (`bin/db-common.xml:134`): `js-ant init-js-db-pro` (and `-ce`) drops, creates and initialises the repository schema, the same target the newdb script runs before its import. The forward procedure is therefore reversible with the old buildomatic: initialise the old schema, then `js-import` the point-B export into it. Nothing else is needed, and jrsctl holds every input: the restored buildomatic with its `default_master.properties`, the keystore backup and the export with its hash.

## Decision

1. **`upgrade rollback <runId> --to-point B|C --restore-database` rebuilds a newdb run's database.** Two steps follow `restore-jrsctl-config` and precede `start-service` in the rollback plan: `rebuild-database` runs `js-ant init-js-db-<ce|pro>` from the restored buildomatic, and `reimport-full-export` runs `js-import --input-zip <point-B export> --update --include-access-events --include-audit-events --include-monitoring-events --include-server-settings` through it. The export is the run's own `full-export.zip` or the archive adopted with `--export` (ADR-0028), hash-verified first. Both steps are `irreversible()`: a dropped database has no compensation, the export is the only copy of the old data and the import that follows is what puts it back. Each runs its vendor command at most once per rollback run through a done marker, so a resume never drops a database it already rebuilt.

2. **Only a run whose vendor script started may have its database rebuilt.** `run-vendor-upgrade` writes `snapshots/<runId>/vendor-upgrade.started` (script name and time) the moment it launches the script, forced to disk beside the attempt marker; the compensation that restores point B erases the attempt marker and never this file. `--restore-database` is refused at plan time (exit 2) when the file is absent, since the database is then still the old one and dropping it would destroy the only copy; a run recorded as successful (its `upgrade.json` names the mode) counts as started. A samedb run is refused with exit 6: the script migrated the schema in place, and no export undoes that. Without the flag the rollback stays files only and its plan says how to get the database back.

3. **The backup question is samedb's.** `confirm-db-backup` and the CLI gate apply to `--mode samedb` only, with the reason in the message: "samedb migrates the repository database's schema in place; an export cannot undo that, so back up the database yourself and pass --db-backup-confirmed". A newdb plan carries no gate and says instead: "jrsctl backs up the files, the keystore and a full export of the repository; js-upgrade-newdb drops and recreates the database from that export, and upgrade rollback --restore-database rebuilds it from the same export". The guided menu and the console form follow: newdb asks nothing, samedb asks. `--db-backup-confirmed` on a newdb command line is accepted and ignored, so existing scripts keep working.

4. **Before the vendor commands run, the database must answer** when jrsctl has a `database` section to ask it with (`JdbcSettings`), and the restored buildomatic must ship `js-ant` and `js-import`; `vendor.javaHome` must be set. A precheck failure leaves the files restored and the database untouched.

## Consequences

- `UpgradeOperations.RollbackOptions(toPoint, restoreDatabase)`; `planRollback(runId, point)` stays as a default method for the files-only case. `PlanRegistry` round-trips `restoreDatabase` for `runs recover`.
- `SnapshotSet.vendorStarted()`/`vendorScriptStarted()`; `DatabaseRestoreSteps` in `ops`; `IdempotencyCoverageTest` lists both steps.
- Spec §10.1 no longer says "both modes require `--db-backup-confirmed`"; the sentence "Rollback restores files only" is samedb's and the files-only rollback's, not newdb's.
- The rebuilt database is the old repository as of the export: a scheduled job that fired, or a user edited, between the export and the rollback is gone. The plan says so in its own words. With ADR-0025 the window is the vendor run itself, since the service stays stopped between the export and the script.
- Not verified live. The fakes prove the order (init, then import), the arguments and the refusals; the first `--restore-database` against a real newdb run should be recorded in `BUILD_STATUS.md`. `init-js-db-*` on a database the vendor script left half-created is the vendor's own recovery path (upgrade guide: "re-run the upgrade" after fixing the cause), which is why the step's failure text sends the operator to the buildomatic log rather than promising a clean state.
