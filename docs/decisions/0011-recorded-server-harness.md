# ADR-0011: The adapter contract runs against recorded servers, one per compat-matrix row

Status: accepted · Date: 2026-09-11 · Spec: §0 rule 10, §16, §19 Q6, §20

## Context
Spec §20 makes "the `needs-jrs` adapter contract suite green across every version in `compat/matrix.yaml`" a release gate, and §16 places that suite in a nightly Testcontainers run against every JasperReports Server image in a private registry. No such registry or image exists (§19 Q6 is open), the build machine has no Docker, and the one `needs-jrs` test (`LiveJrsContainerTest`) pointed at a placeholder image that can never pull. The gate was therefore unmeetable, and the adapter's behaviour per server version was covered only by hand-written WireMock stubs in unit tests, plus ten recorded `serverInfo` bodies. Assessment item 5.3 ("no real-JRS substitute") and roadmap item 11 asked for a recorded-fixture harness so the suite can run per matrix row without Docker.

## Decision
The adapter contract, the three calls `LiveJrsContainerTest` makes (`identity()`, `capabilities()`, `health()`), runs in the ordinary unit-test phase against **recorded servers**: one directory per `<version>-<edition>` under `jrs/src/test/resources/recordings/`, in WireMock's stub format, with a `recording.json` naming the server and its provenance. `RecordedJrsContractTest` replays every recording through the real `RestJrsAdapter` and asserts the identity the recording claims, that the probed capabilities equal exactly what the matrix expects for that row, and that health passes. It also fails when any matrix range × edition has no recording, and when any recording file carries an `Authorization` matcher, a form password or a cookie.

Two provenances are allowed and distinguished. `recorded` directories come from `RecordJrsTest`, which proxies the contract calls through WireMock's recorder at a live server and writes the sanitised exchanges; `10.0.0-PRO` was recorded this way from the 10.0.0 PRO install on the build machine. `synthesised` directories replay the `serverInfo` body captured from a real server of that version and answer the probes the way the matrix says that row does; they prove the adapter and the matrix agree, not that the server does, and their metadata says so. The nine other rows are synthesised today and are replaced by recordings as servers become available, with no change to the test.

`LiveJrsContainerTest` stays, tagged `needs-jrs`, for the day Q6 names an image; it is a stronger check, not a different one. The `integration` CI job leaves the release gate (ADR-0007 is deferred and the job runs zero tests); the recorded suite runs inside `build` on both operating systems, so the §20 clause is met on every push rather than never.

## Consequences
Every compat-matrix row is exercised end to end through the adapter on every build, on any machine, in about a second per row. A new matrix row without a recording fails the build, which is the intended pressure. A synthesised recording cannot catch a server that deviates from the matrix; a recorded one can, so the value of the harness grows with each real recording, and `recording.json` keeps the difference honest. Recordings contain nothing secret by construction and by test. Spec §16 and §20 are amended: the release gate reads "recorded contract suite green across every matrix row, and the live suite where an image exists".
