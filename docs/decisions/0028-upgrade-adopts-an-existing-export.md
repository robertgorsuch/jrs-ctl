# ADR-0028: `upgrade --export` adopts an export taken earlier or elsewhere, decrypted by alias

Status: accepted, 2026-09-18. Extends ADR-0012 and ADR-0025.

## Context

A newdb upgrade is `js-upgrade-newdb <export>`: the vendor script drops the repository database, recreates it with the target schema and imports the export it was given (ADR-0012). Until now jrsctl always took that export itself, with the service stopped, into `snapshots/<runId>/full-export.zip` (ADR-0025), and nothing else could stand in for it: the path was derived from the run id, and the run id is not known before the run.

The second field test of v1.6.0 (`docs/reviews/2026-09-18-field-test-2-review.md`, U5b, and the tester's second round) asked for the case the vendor's own upgrade guide starts from: an export that already exists. It was taken on a schedule, or by hand with `js-export --everything`, or on another server altogether, since "an upgrade is not always linear": a repository is moved from one environment to a fresh installation of the new version, sometimes with a different keystore. The tester's words: options to alter the upgrade plan should exist.

What the vendor tooling allows was checked on the 10.0.0 buildomatic on this machine (`bin/upgrade-newdb.help`, `bin/import-export.xml`): the newdb script takes the export path and at most one option word (`with-samples`, `include-access-events`, `regen-config`, `test`), so nothing about keys ever goes on its command line; every import buildomatic runs passes `--keyalias=${deprecatedImportExportEncSecret.keyalias}` and `--keypass=${deprecatedImportExportEncSecret.keypass}` read from `default_master.properties`; without them the import decrypts with the keystore buildomatic resolves through `keystore.init.properties`, which `stage-keystore-init` writes (ADR-0016 lineage, spec §10.2 step 8a). An export made portable (`js-export --keyalias deprecatedImportExportEncSecret`, or `jrsctl export --portable` once Task 11 lands) is therefore decryptable on any server through the alias; an export encrypted with another server's own key is decryptable only with that server's keystore files.

## Decision

1. **`upgrade --export <file>` adopts an existing export, newdb only.** The plan replaces `full-export` with `adopt-full-export` (phase `vendor-upgrade`, before `run-vendor-upgrade`). Its precheck requires the file to exist and to be an export archive (a ZIP whose root holds `index.xml`; `ExportArchives.problem`); its execute hashes the file and writes `snapshots/<runId>/full-export.external` holding the path and the SHA-256, nothing copied; compensation removes that record. `run-vendor-upgrade` resolves the export through `SnapshotSet.resolveFullExport()` (the record when present, else the run's own archive) and its precheck refuses when the file's hash no longer matches the record. `record-upgrade` lists the adopted file in `upgrade.json` under `external:<path>` with its hash. The rollback plan's warning names the adopted archive as the repository-level backup to re-import. With `--mode samedb` the option is a usage error (exit 1): samedb migrates the database in place and imports nothing.

2. **An export from another server or version is a warning, never a refusal.** When a `.jrsctl.json` sidecar sits beside the archive and names another server identity or version, the plan warns with both and points at `--key-alias`; with no sidecar it warns that the origin cannot be checked. The tester's case is exactly this one, so the tool says what it knows and proceeds. The plan always warns that `js-upgrade-newdb` rebuilds the repository from that export and discards every change made after it was taken.

3. **`--key-alias <alias>` and `--key-password-ref <ref>` use the vendor's own decryption route.** The alias is written by `write-master-properties` into the staged `default_master.properties` as `deprecatedImportExportEncSecret.keyalias`; a password reference is resolved at execute time, registered with the redactor, written as `deprecatedImportExportEncSecret.keypass` and zeroed. This is the one password key jrsctl writes into a vendor properties file itself, an exception to spec §7.4's rule that jrsctl never adds a key whose name contains `pass`: the operator asked for it by name, it is the only way the vendor tooling accepts it (the script's command line takes no key), the file lives in the target package's buildomatic, which the operator owns, and the step's compensation puts the pristine file back. Either option without `--export`, or the password without the alias, is a usage error (exit 1).

4. **`--source-keystore` is deferred.** The plan (D9) also described adopting the source server's `.jrsks`/`.jrsksp` as this server's keystore after the vendor run. That route replaces the server's keystore, and the plan's own gate for it is a live newdb upgrade against a copy of the real installation, which cannot be run safely on this machine today (the copy would share the installation's database and service). It is not shipped, not hidden: this ADR records it as pending, the `--help` text does not mention it, and the operator guide names the vendor's procedure (copy the keystore files by hand before the upgrade, security guide 10.1) for that case. `import --source-keystore` (ADR-0020) remains for the import command.

## Consequences

- `UpgradeOptions` gains `existingExport`, `keyAlias`, `keyPassword`; `PlanRegistry` round-trips the three for `runs recover`; the plan fingerprint includes them through the options.
- The adopted file is never copied under the home: the space budget (Task 6) no longer reserves the export's estimate for it, and the operator keeps the file where it is until the run has finished; `adopt-full-export` says "not copied" in its detail line.
- `IdempotencyCoverageTest` lists `AdoptFullExport`; re-execution rewrites the same record, compensation removes it and leaves the operator's file alone.
- Not verified live: the alias route against the 10.0.0 server on this machine. The fakes prove the properties reach the staged file and the export reaches the wrapper; the first live newdb upgrade from a portable export should be recorded in `BUILD_STATUS.md`.
