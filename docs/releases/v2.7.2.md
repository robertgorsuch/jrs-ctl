# jrsctl 2.7.2

jrsctl 2.7.2 is a patch release with fixes from the first field test of `repository load` and `import verify` on a real JasperReports Server 10.0.0 PRO: a 10.0 buildomatic, a PostgreSQL database and a `js-export --everything` archive, on Windows (#310, #311). With these fixes the load ran end to end there. Nothing else changes: JasperReports Server 7.1 to 10.x on Apache Tomcat, on Windows or Linux (64-bit), with a bundled Java 21 runtime.

Download the archive for your system below, check it against its `.sha256` and its signature (`SECURITY.md`), and unpack it. It includes its own Java; nothing needs to be installed on the server.

## Read this before upgrading from 2.7.1

| What changed | What to do |
|---|---|
| **A failure in `repository load`'s create, initialise or load step now rolls back the whole run** (#319): the schema is dropped, then `js-ant clean-config` removes the rendered `build_conf/default`, which holds the database password in clear. The run reports itself rolled back to `preflight`. | Nothing. Rerun the load once the cause is fixed; `render-config` renders the configuration again. |
| **`repository load` refuses a stale buildomatic `iecp.jar`** at `verify-buildomatic` (exit 2, nothing created), and `upgrade` refuses one at `verify-target-package` before the service stops (#315). `doctor`'s `vendor` item warns about it. | Delete the file the message names. buildomatic rebuilds it on its next import. |
| **`repository load` no longer passes the archive's own key alias to `js-import`** (#312). Only the Legacy alias `deprecatedImportExportEncSecret` from `index.xml` is passed, as `jrsctl import` already did. | If you added `--key-alias` only to work around this, you can drop it. |
| **New `--source-database <name>` on `repository load` and `export record`** (#317). The source database is also kept in the sidecar as `sourceDatabase`. `repository load` refuses with exit 6 when `--schema` names the source database, compared without regard to case. | Pass `--source-database` (or record it with `export record`) when the export came from a server whose database `config.yaml` does not name. |
| **The `schema.created` marker has three lines now** (#316): the schema, `state=creating|created|uncertain`, and the instant the schema was seen absent. A 2.7.1 one-line marker reads as `created`. | Nothing. |

No configuration key changed. The new flags are optional.

## Fixed

- **`repository load` failed in `js-import` on a plain `js-export` archive** (#312). The key alias read from `index.xml` is the server's own import/export key, which `--keyalias` does not accept, so the vendor import died in `BaseExporterImporter.getCipher` and the run rolled back.
- **A wrong password could lock the account** (#313). After a 401, each later `doctor`, `smoke` and `import verify` item logged in again. One round of the three sent ten failed logins and left `superuser` disabled. jrsctl now sends a refused credential once per command. Later items report "not sent: the server already refused these credentials in this jrsctl run". A 403 does not count, and a different credential is sent normally. The credential is recognised by an HMAC under a per-process key and its value is not kept.
- **`import verify` reported present resources as missing** (#314). `js-export` escapes characters in entry names as `-` plus four hex digits (`-` itself is `-002d`). Ids are now decoded one path segment at a time. On the field archive, all 1235 resources were found, where 163 had been reported missing.
- **The vendor Ant import failed with `NoClassDefFoundError` after a hotfix** (#315). `make-ie-classpath-jar` builds `conf_source/<edition>/lib/iecp.jar` only when it is missing, so a hotfix that replaced jars left it naming files that are gone. jrsctl now refuses before anything changes and names the file to delete (ADR-0054). It does not delete the file itself.
- **`repository load` could mark a schema it had not created** (#316). `create-js-db` checks the catalogue again right before writing the marker. A schema that appeared after `verify-target-schema` fails the step with no marker, so nothing is dropped. If the create target fails and the schema exists, the marker reads `uncertain`. The compensation then refuses (exit 4) and prints the `DROP DATABASE` statement for the DBA (ADR-0055).
- **The source-database collision check was narrower than ADR-0052 describes** (#317). It now covers the configured `database.url`, `--source-database` and the sidecar's `sourceDatabase`. The stored plan keeps the value for `runs recover`.
- **Windows: vendor `.bat` wrappers failed when a Unix `find.exe` came first on the PATH** (#318), for example in Git Bash. For a batch child, the PATH jrsctl passes is the vendor Java `bin`, then `%SystemRoot%\System32`, `%SystemRoot%` and `%SystemRoot%\System32\Wbem`, then the inherited PATH. Running the wrappers by hand from such a shell still fails; the operator guide says so.
- **Smaller field-test findings** (#319):
  - `init --tools-only` takes `vendor.javaHome` from the distribution's bundled `java` folder when it has a launcher, and falls back to `JAVA_HOME` otherwise.
  - The REST full-server export plan says calendars are included on 10.0 and later (#310) and not confirmed below 10.0.
  - `repository load` names a recorded sidecar's export format and source version.
  - Plan summaries list rollback points in plan order.
  - The `export record` summary lists calendars when the archive has them.
  - `runs list` and `runs show` show a pending run that does not hold the run lock as "interrupted".
  - The `repository load` plan warns that the vendor default admin passwords stay in place.

## Known limitations

- **`repository load` has run against a live server on one machine only.** The tested setup was a 10.0.0 PRO buildomatic, PostgreSQL, Windows and a 10.0 source archive. The schema-marker states, the source-database check, the Windows PATH order and the whole-run rollback (#316 to #319) are tested against fake vendor scripts and a fake JDBC catalogue only. In that test, three failed loads and one `runs recover --rollback` after a killed run each dropped only their own schema. Neither an 8.2 source nor Linux has been tried. Try the load on a copy of a repository first, and keep the DBA's `DROP DATABASE` for the schema it names ready.
- **A jrsctl `export` does not record `sourceDatabase`.** Use `--source-database` or `export record`.
- **`passwords migrate` has never run against a live server**, and needs the deployed webapp on its host. jrsctl does not run inside a container (ADR-0043).
- **`repository load` supports PostgreSQL and MySQL.** Oracle, SQL Server and DB2 are refused while planning with exit 6.
- **The REST `everything` export below 10.0 may lack calendars.** `export --full-server` on the server host is `js-export --everything` and carries them.
- **`import verify` compares by id, not by content.**
- **jrsctl does not move a Windows service or systemd unit to a new Tomcat.**
- **Paths verified only against fake vendor scripts:** as listed in the 2.7.0 notes, apart from the field-tested `repository load` above.
- **Other open limitations, as in 2.7.0:**
  - a buildomatic on a network share (#31);
  - the adapter against live servers other than 10.0.0 PRO (#35);
  - Windows containers are not detected;
  - `logs/jrsctl.log` is not rotated;
  - the pager in unusual consoles.
