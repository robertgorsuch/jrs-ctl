# jrsctl 2.5.0

jrsctl 2.5.0 collects the fixes from a fifth field test: a JasperReports Server 9.0.0 PRO to 10.0.0 upgrade on Windows, in a WAR-file layout, into a new Tomcat (`--tomcat-dir`). Everything else stays as 2.4.0 shipped it: JasperReports Server 7.1 to 10.x on Apache Tomcat, on Windows or Linux (64-bit), with a bundled Java 21 runtime.

Download the archive for your system below, check it against its `.sha256` and its signature (`SECURITY.md`), and unpack it. It includes its own Java; nothing needs to be installed on the server.

## Read this before upgrading from 2.4.0

| What changed | What to do |
|---|---|
| **`upgrade` skips locked files by default** (ADR-0045). A file the running server holds a byte-range lock on (the Bitronix journals `WEB-INF/logs/transactionBtm*.tlog` of any server that has used a Virtual Data Source) is left out of the webapp backup, named in the step output and in `<archive>.skipped`, and the plan warns. `--skip-locked-files` is still accepted and changes nothing; the new `--no-skip-locked-files` restores the 2.4.0 behaviour; both together exit 1. | For an in-place upgrade (no `--tomcat-dir`), pass `--no-skip-locked-files` if you want a complete backup or nothing: a point-B restore does not recreate skipped files. |
| **`upgrade --mode newdb --tomcat-dir` exits 2 without `--db-rebuild-confirmed`** (ADR-0047). The vendor script drops and rebuilds the database the installed `default_master.properties` names, which is the database the old server still uses, even when the new server goes into a new Tomcat. Every newdb plan now names that database in a warning. `--test` is exempt; the guided menu asks before passing the flag. | Add `--db-rebuild-confirmed` only once the old server need not keep working. A 2.4.0 command line of this shape now stops with exit 2 before planning. |

No configuration key changed. Runs planned by 2.4.0 recover with the plan they fingerprinted: the new defaults live in the command line, not in the stored arguments.

## Fixed

- **The vendor upgrade stopped at a consent question** (ADR-0046). In every upgrade but `test`, the 10.0 buildomatic asks on stdin to confirm a Compact installation stays Compact; jrsctl gives a vendor script no stdin, so Ant failed with `unexpected end of stream while reading input` while the wrapper still said "Ant return code: OK". `write-master-properties` now stages `SKIP_UPGRADE_CONSENT=true`. The installation type is already checked by `verify-target-package`.
- **The webapp backup failed on every server with a Virtual Data Source.** See ADR-0045 above.
- **`backup-config` refused a buildomatic beside the installation.** On a WAR-file install `server.buildomaticDir` lies outside the installation and Tomcat directories, and the snapshot refused `default_master.properties` as "outside" after a twelve-minute webapp backup. The snapshot base is now the deepest directory that holds the installation, Tomcat and every configuration file; `verify-target-package` refuses a layout with no common root (two Windows volumes) before any backup starts.
- **A failed vendor run quoted stack frames.** Once a vendor run reports a failed build, the lines a failure message quotes start at `BUILD FAILED` and leave out stack frames, instead of being the last 20 lines.
- **Point B after a side-by-side vendor failure ended "rollback incomplete"** (ADR-0048). With `--tomcat-dir`, the compensation of a failed `run-vendor-upgrade` tried to rename the old webapp and installed buildomatic aside, which the vendor script never touched and which Windows refused while the old server held them open (exit 4 in both field runs; nothing was damaged). It now leaves them in place and still restores the configuration and keystore. A point-B tree restore that fails names the exception type.
- **`upgrade rollback --to-point B|C` after a side-by-side upgrade** (ADR-0049). It no longer restores the old webapp and the installed buildomatic for a run made with `--tomcat-dir` (read from the arguments stored with the run's plan, so earlier runs are covered too). It restores the configuration, keystore and `config.yaml` as before and warns which Tomcat to start. Before this, after a finished run it extracted the old webapp into the new Tomcat, because `config.yaml` already named it.
- **The doctor lines about the run's own pending row and lock** inside an upgrade now say "this run itself" instead of "judged against the target".

## Known limitations

- **A newdb upgrade cannot keep the old server running.** A separate target database (ADR-0047, option B) is not supported: the old server loses its repository once the vendor script rebuilds it.
- **jrsctl does not move a Windows service or systemd unit to a new Tomcat.** After an upgrade with `--tomcat-dir` (which requires `service.kind: manual`), and after rolling one back, register or start the right Tomcat by hand as the run's output says.
- **A restore of an archive with a `.skipped` record does not recreate those files and does not say so.** Check the record before an `upgrade rollback` of an in-place run.
- **Paths verified only against fake vendor scripts, never against a live installation:** `upgrade --export` and `upgrade --test`; `upgrade rollback --restore-database`; the key alias reaching the vendor import; the vendor strategy's rollback of new content; the Linux service paths; an official hotfix package from support (checked against the documented layout only). The 2.5.0 upgrade fixes were checked against a fake buildomatic that asks the same consent question; try an upgrade on a copy of the server first.
- **Buildomatic on a network share** (#31): `doctor`, `init` and a vendor export were verified over UNC paths, mapped drives and a Linux gvfs mount; a vendor import or an upgrade with the tree on a share, and a kernel CIFS or NFS mount, were not. A raw UNC path does not work for the vendor tools; use a mapped drive letter.
- **The adapter was never tested against a live server of any version other than 10.0.0 PRO** (#35). The other rows of the compatibility matrix are covered by recordings synthesised from their `serverInfo` fixtures.
- **Windows containers are not detected.** The container check recognises Docker, Podman and Kubernetes on Linux.
- **`logs/jrsctl.log` is not rotated.** Delete or archive it by hand when it grows; `runs support-bundle` reads only the run's own lines and the last 200.
- **The pager** reads single keys through the guided menu's JLine terminal. If it misbehaves in an unusual console, `--no-pager` prints everything at once.
