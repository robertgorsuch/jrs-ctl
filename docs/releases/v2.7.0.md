# jrsctl 2.7.0

jrsctl 2.7.0 adds the two commands that a newdb-style upgrade still left to the operator's hands: `repository load`, which creates and loads a new repository schema on a new version's buildomatic while the old server keeps running, and `passwords migrate`, the vendor's password migration as a command of its own. Both answer a customer upgrade guide reviewed against the tool, and both have been verified against fake vendor scripts only; a run against a real database server and a real 10.1 server is still to come, and the release notes say so wherever it matters. Everything else stays as 2.6.0 shipped it: JasperReports Server 7.1 to 10.x on Apache Tomcat, on Windows or Linux (64-bit), with a bundled Java 21 runtime.

Download the archive for your system below, check it against its `.sha256` and its signature (`SECURITY.md`), and unpack it. It includes its own Java; nothing needs to be installed on the server.

## Read this before upgrading from 2.6.0

| What changed | What to do |
|---|---|
| **A new configuration shape, tools-only** (ADR-0052). `init --tools-only --remote <url> --buildomatic-dir <dir>` writes a configuration that names a buildomatic and no installation. `doctor` reports the installation items as *tools-only configuration* and keeps `vendor`, `vendor-java` and `database`; its `database` item asks the database server's catalogue whether the schema the URL names exists. `export` and `import` treat the shape as REST-only; `hotfix` and `upgrade` still need an installation. | Nothing, unless you want `repository load`: then write a second jrsctl home for it (`--home`), since one home holds one configuration. |
| **`PlanRegistry` rebuilds two more plans for `runs recover`** (`repository.load`, `passwords.migrate`). | Nothing. Runs planned by 2.6.0 recover with the plan they fingerprinted; no stored argument changed shape. |

No configuration key changed.

## New

- **`jrsctl repository load --schema <name> --from <export> [--include-events] [--key-alias <alias>]`** (#279, ADR-0052, spec §10.5): the vendor's manual alternative to `js-upgrade-newdb` (upgrade guide 10.1 p.62) as one journaled plan from a tools-only configuration. Phases `preflight` (`doctor`, `verify-buildomatic`, `verify-target-schema`, `adopt-export`, `render-config`), `create` (`create-js-db`), `initialise` (`init-js-db-<ce|pro>`, `import-minimal-<ce|pro>`), `load` (`js-import --input-zip <export> --include-server-settings`), `verify` (`record-load`). It refuses while planning when the configuration is not tools-only, when the database type has no catalogue rule (PostgreSQL and MySQL have one; others exit 6) and when `--schema` is the configured server's own database (exit 6). Before anything is created it refuses when `js.dbName` in `default_master.properties` is not the schema, when `appServerType` is not `skipAppServerCheck`, and when the schema already exists; it never edits that file and never drops a schema it did not create. A failure after `create-js-db` drops exactly the schema this run created, by name over JDBC and only while `default_master.properties` still names it; otherwise exit 4 names the `DROP DATABASE` statement for the DBA.
- **`render-config`**, the last preflight step of `repository load` (#279 item 6): `js-ant clean-config` then `js-ant gen-config`, so the buildomatic renders its configuration before any schema step reads it. The rendered `metadata.jdbc.url` must name `--schema` on the database server the plan was made for, else the step fails, `clean-config` undoes it and the run ends with exit 3 and nothing created. The rendered properties are kept, every password masked, under `snapshots/<runId>/rendered-config`, and `repository-load.json` lists their hashes: a configuration baseline for the new server.
- **`jrsctl passwords status [--json]`** (#284, ADR-0053, spec §10.6): read-only, in the `doctor` layout: the deployed webapp's `password.strategy`, the vendor tools, and the counts `js-ant detect-password-strategy` prints (PASS when the migration is complete, WARN naming the users still on legacy passwords, FAIL when the utility fails). Exit 0 or 2; exit 6 below 10.1.
- **`jrsctl passwords migrate --db-backup-confirmed [--cleanup]`** (#284, ADR-0053): `migrate-passwords-dry-run`, `migrate-passwords` (permanent; the only way back is a database restore, which the flag vouches for and the run audits), `detect-password-strategy`, and with `--cleanup` the vendor's `cleanup-password-migration`, as one journaled plan while the server keeps running. Without the flag the command prints the installation guide's backup requirement and exits 2 before planning. Needs the installation on the host, since the utility reads the deployed webapp's settings file; a REST-only or tools-only configuration is refused with exit 2. `upgrade --migrate-passwords` is unchanged.
- **`init --tools-only`** (ADR-0052): see the table above.

## Known limitations

- **`repository load` and `passwords migrate` have never run against a live server.** Every step is tested against fake `js-ant` and `js-import` scripts and a fake JDBC catalogue; the real `gen-config` output format was read from a 10.0.0 buildomatic. Try `repository load` on a copy of a repository first, and keep the DBA's `DROP DATABASE` for the schema it names ready.
- **`repository load` supports PostgreSQL and MySQL.** Oracle, SQL Server and DB2 have no catalogue rule yet and are refused while planning with exit 6; the vendor targets by hand remain the route there.
- **`passwords migrate` needs the deployed webapp on its host**, and jrsctl does not run inside a container (ADR-0043). A containerised deployment migrates passwords with the vendor's `js-ant` targets inside the task, or deploys the webapp on a VM for the migration.
- **The REST `everything` export may lack calendars.** The REST API reference does not list them; `export --full-server` on the server host is `js-export --everything` and carries them.
- **`import verify` compares by id, not by content.** It says what an import left out, not whether what arrived is identical.
- **`customizations scan --installed`** was written for a tree extracted from a container image and has not been run against one in the field.
- **jrsctl does not move a Windows service or systemd unit to a new Tomcat.** After an upgrade with `--tomcat-dir` (which requires `service.kind: manual`), and after rolling one back, register or start the right Tomcat by hand as the run's output says.
- **Paths verified only against fake vendor scripts, never against a live installation:** `upgrade --export` and `upgrade --test`; `upgrade rollback --restore-database`; the key alias reaching the vendor import; the vendor strategy's rollback of new content; the Linux service paths; an official hotfix package from support; the ten review fixes of 2.6.0.
- **Buildomatic on a network share** (#31), **the adapter against live servers other than 10.0.0 PRO** (#35), **Windows containers are not detected**, **`logs/jrsctl.log` is not rotated**, **the pager** in unusual consoles: as in 2.6.0.
