# jrsctl 2.4.0

**This is the final release of jrsctl**, replacing 2.3.0 in that role. It exists for one reason: a field upgrade of a 9.0.0 server on Windows could not be backed up while the server was running, and stopping the server earlier was not an option for that installation. Everything else stays as 2.3.0 shipped it: JasperReports Server 7.1 to 10.x on Apache Tomcat, on Windows or Linux (64-bit), with the same bundled Java 21 runtime. To continue the work, fork the repository.

Download the archive for your system below, check it against its `.sha256` and its signature (`SECURITY.md`), and unpack it. It includes its own Java; nothing needs to be installed on the server.

## Read this before upgrading from 2.3.0

| What changed | What to do |
|---|---|
| **`backup-webapp` names the file it cannot read.** When the archive of the running server's webapp (and the source buildomatic) hits a file another process holds a byte-range lock on, the step fails as before (exit 3, nothing mutated), but the message now carries the file's path and a remediation that says how to find the holder. | Nothing. A run that used to fail still fails at the same place; it now tells you which file. |
| **New `upgrade --skip-locked-files`** (ADR-0044). With it, a file that opens but cannot be read is left out of the archive, with no partial entry. Each skipped file is named in the step output and listed in `<archive>.skipped` next to the archive; the plan carries a warning before the run; the stored arguments and the fingerprint carry the choice, so `runs recover` archives the same way. | Use it only for an upgrade into a new Tomcat (`--tomcat-dir`), where the old webapp is left as it was and the archive is a safety copy. For an in-place upgrade an incomplete backup is worse than a stopped run, which is why skipping is never the default. |

No exit code or configuration key changed. The `upgrade` plan fingerprint is unchanged for a plan that does not use the new option.

## Fixed

- **The webapp backup failed without naming the file.** Two newdb upgrades of a 9.0.0 server on Windows (field test, 2026-10-12) failed in `backup-webapp` after three to five minutes with `The process cannot access the file because another process has locked a portion of the file`, both leaving the same partial archive, so the lock was held continuously. The read error carries only the operating system's text, and the step passed it through with a remediation about disk space. The archive writer now wraps a read failure with the path of the file, and the step's remediation names the file, the tools that identify its holder (Resource Monitor, `handle.exe`) and the new option.
- **`UpgradeOptions.withKeyPassword` dropped `migratePasswords`.** Every `with` method now keeps every other field.

## Added

- **`upgrade --skip-locked-files`.** The archive reads the first chunk of each regular file before it writes the entry header, so a file that cannot be read is either an error naming the path (default) or, with the option, left out cleanly. A read that fails after the first chunk is always an error: an entry already begun cannot be taken back. The step writes `<archive>.skipped` (one absolute path per line) beside a finished, hashed archive, logs a warning per file and reports the count.

## Documentation

- **ADR-0044:** why the file is named, why skipping is on request only, and the options rejected (stopping the server first, always skipping, Volume Shadow Copy).
- **Spec §10.2 step 6 and §10.4, the operator guide and the spec changelog:** the new behaviour and option.
- **README, `README.txt`, `SECURITY.md`, `CONTRIBUTING.md`, `BUILD_STATUS.md`:** 2.4.0 is now the final release.

## Known limitations

These stay as they are; there will be no later release to change them.

- **A restore of an archive with a `.skipped` record does not recreate those files and does not say so.** Check the record by hand before an `upgrade rollback` of a run that used `--skip-locked-files`. For an upgrade into a new Tomcat the old webapp is untouched, so there is nothing to restore.
- **The new option was not run against the field installation before release.** The tests hold a real byte-range lock in the test process, which Windows enforces across handles, so they reproduce the field error exactly; on Linux a lock is advisory and the tests are skipped there.
- **Paths verified only against fake vendor scripts, never against a live installation:** `upgrade --export` and `upgrade --test`; `upgrade rollback --restore-database`; the key alias reaching the vendor import; the vendor strategy's rollback of new content; the Linux service paths; an official hotfix package from support (checked against the documented layout only). Try an upgrade on a copy of the server first.
- **Buildomatic on a network share** (#31): `doctor`, `init` and a vendor export were verified over UNC paths, mapped drives and a Linux gvfs mount; a vendor import or an upgrade with the tree on a share, and a kernel CIFS or NFS mount, were not. A raw UNC path does not work for the vendor tools; use a mapped drive letter.
- **The adapter was never tested against a live server of any version other than 10.0.0 PRO** (#35). The other rows of the compatibility matrix are covered by recordings synthesised from their `serverInfo` fixtures.
- **Windows containers are not detected.** The container check recognises Docker, Podman and Kubernetes on Linux.
- **`logs/jrsctl.log` is not rotated.** Delete or archive it by hand when it grows; `runs support-bundle` reads only the run's own lines and the last 200.
- **The pager** reads single keys through the guided menu's JLine terminal. If it misbehaves in an unusual console, `--no-pager` prints everything at once.
