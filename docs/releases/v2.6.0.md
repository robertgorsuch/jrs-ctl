# jrsctl 2.6.0

jrsctl 2.6.0 adds what a repository move needs when the server jrsctl is pointed at runs in a container or on a host the operator cannot reach with the vendor tools: a full-server export over REST, a sidecar for an archive made by hand, a check that an import left nothing out, a pause for the report jobs an import adds, and a scan of a webapp tree extracted from an image. It also carries the ten fixes of the October upgrade-module review and the analytics JNDI check on 10.x targets. Everything else stays as 2.5.0 shipped it: JasperReports Server 7.1 to 10.x on Apache Tomcat, on Windows or Linux (64-bit), with a bundled Java 21 runtime.

Download the archive for your system below, check it against its `.sha256` and its signature (`SECURITY.md`), and unpack it. It includes its own Java; nothing needs to be installed on the server.

## Read this before upgrading from 2.5.0

| What changed | What to do |
|---|---|
| **`export --full-server` works from a machine with no installation** (ADR-0051). With `init --remote`, where it used to be refused, a full-server export is now the server's REST export with the `everything` parameter. The REST API reference lists repository resources, permissions, report jobs, users, roles and server settings for it and does not mention calendars; the plan says so. On the server host nothing changes: `js-export --everything` as before. | If the calendars matter, run `export --full-server` on the server host. `--stop-service` has no effect on the REST route and the plan says that too. |
| **`check-analytics-jndi` runs for every upgrade target from 9.0 on**, not 9.0.x only, and `doctor` gains an `analytics-jndi` item (#268). Both are warnings. | A `context.xml` carried over from 8.x without `jdbc/jasperserverSystemAnalytics` and `jdbc/jasperserverAuditAnalytics` now earns a warning on 10.x; add the two resources (upgrade guide 10.1 p.93). |

No configuration key changed. Runs planned by 2.5.0 recover with the plan they fingerprinted: `import --pause-jobs` joins the stored arguments as `pauseJobs`, absent meaning `false`, and enters the fingerprint only when set.

## New

- **`jrsctl import verify <archive>`** (#262): after an import, a read-only report of whether every organisation, user, role, folder and resource the archive holds is on the server, read from the archive's own layout and the server's REST directory and repository listings. One `doctor`-style item per kind; exit 2 when anything is missing or the server could not be asked; `--uris` lists every missing id in the JSON report.
- **`jrsctl export record <archive>`** (#263): writes the `.jrsctl.json` sidecar for an archive `js-export` made by hand, from the archive's SHA-256 and its `index.xml` (folders, modules, the full-server judgement, `jsVersion`), plus `--source-version`, `--source-keystore` (for the fingerprint only) and `--key-alias`; the Legacy alias is read from the index. `import` then verifies the hash, scopes its snapshot, adopts the alias and applies the themes rule as for an exported archive. Sidecars gain an `origin` field (`export` or `record`).
- **`jrsctl import --pause-jobs`** (#264, ADR-0050): lists the server's report jobs before the import and, in a `jobs` phase of its own after it, pauses the ones the import added, so a repository imported beside a running source does not deliver every report twice. Best effort: a refused pause is a warning naming the ids and the call to make by hand, never a rollback of the finished import; a rollback resumes exactly the ids it paused.
- **`jrsctl customizations scan --installed <dir>`** (#266): compares an explicit tree, a webapp directory or a Tomcat tree holding one as extracted from a container image, instead of the configured installation. Runs with no `config.yaml`; registers nothing (`--register` with it is a usage error); `--tomcat` lists that tree's Tomcat-side files.
- **Diffs for installer-written files in the scan** (#267): an `INSTALLER` entry whose file the vendor copy also has (`META-INF/context.xml`, `WEB-INF/js.quartz.properties` and the others) carries the unified diff from the vendor copy, under the table and as `diff` in `--json`, since such a file can hold a site's own change beside the installer's values. `customizations register` accepts such a file with a warning that an upgrade will most likely report a `CONFLICT` for it.
- **`export --full-server` over REST from another machine** (#265, ADR-0051): see the table above.
- **`doctor` item `analytics-jndi`** and `check-analytics-jndi` on 10.x targets (#268): see the table above.

## Fixed

The upgrade-module review of 2026-10-28 and 29 (PRs #249 to #252) fixed ten defects, each reproduced by a failing test first; none of them had been reported from the field:

- A point-B restore across volumes copied straight to the target, so a copy that failed half-way left a partial tree; it now stages in a `.part` sibling and renames into place.
- `upgrade rollback` of a side-by-side run whose stored plan was missing restored the old webapp into the new Tomcat; a point-B manifest whose webapp differs from the configured one now marks the run as side-by-side (ADR-0049 amended).
- `rebuild-database` chose the CE or Pro schema from the webapp name alone; `record-upgrade` now writes the edition into `upgrade.json` and the rollback reads it, then the server identity, then the name.
- A point-B copy turned a link to a file into a copy, threw on a link to a directory and dropped POSIX permissions, owner and group; links are recreated and attributes kept where both file systems have them.
- A crash between moving a backup into place and writing its `.sha256` made every resume refuse it; an artefact with no record is now taken again with a warning.
- `run-vendor-upgrade` re-hashed only an adopted export, not the run's own point-B export it rebuilds the database from; both are verified now.
- `rebuild-database` and `reimport-full-export` reported ok when their done marker could not be written, so a resume would drop the rebuilt database again; a marker that cannot be written fails the step.
- `--restore-database` for a run recorded before the `vendor-upgrade.started` marker existed was refused only after `stop-service`; plan and steps now share one rule.
- Archive extraction checked each symbolic link on its own, so a chain of links could create one at the root pointing at its parent; a link is never created under another link and a target may use `..` only at its start.
- `write-master-properties` turned the key password into a `String` on the way to the staged file; it is now written from `char[]` and cleared.

## Known limitations

- **A newdb upgrade still cannot keep the old server running.** ADR-0052 designs the separate-schema route (`repository load`); the implementation is issue #279 and is not in 2.6.0.
- **The REST `everything` export may lack calendars.** The REST API reference does not list them; `export --full-server` on the server host is `js-export --everything` and carries them.
- **`import verify` compares by id, not by content.** It says what an import left out, not whether what arrived is identical.
- **`customizations scan --installed`** was written for a tree extracted from a container image and has not been run against one in the field.
- **jrsctl does not move a Windows service or systemd unit to a new Tomcat.** After an upgrade with `--tomcat-dir` (which requires `service.kind: manual`), and after rolling one back, register or start the right Tomcat by hand as the run's output says.
- **Paths verified only against fake vendor scripts, never against a live installation:** `upgrade --export` and `upgrade --test`; `upgrade rollback --restore-database`; the key alias reaching the vendor import; the vendor strategy's rollback of new content; the Linux service paths; an official hotfix package from support; the ten review fixes above.
- **Buildomatic on a network share** (#31), **the adapter against live servers other than 10.0.0 PRO** (#35), **Windows containers are not detected**, **`logs/jrsctl.log` is not rotated**, **the pager** in unusual consoles: as in 2.5.0.
