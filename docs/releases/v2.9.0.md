# jrsctl 2.9.0

jrsctl 2.9.0 fixes what a field dry run of an 8.0.4 → 10.0.0 upgrade on Windows met (#338 to #341, #343, #348), and adds `runs abandon` to close an interrupted run when the server was already put right another way (#350). Two smaller fixes come from the same review: a jrsctl home that is not a folder (#351), and global options written before the command name (#354). Nothing else changes: JasperReports Server 7.1 to 10.x on Apache Tomcat, on Windows or Linux (64-bit), with a bundled Java 21 runtime.

Download the archive for your system below, check it against its `.sha256` and its signature (`SECURITY.md`), and unpack it. It includes its own Java; nothing needs to be installed on the server.

## Read this before upgrading from 2.8.0

| What changed | What to do |
|---|---|
| **Global options before the command name now take effect** (#354). `jrsctl --home <dir> runs list`, `jrsctl --set key=value doctor` and `jrsctl --json …` used to parse and then ignore the option, so the command ran against the default home and configuration. Given in both places, the one after the command name wins; `--set` entries are merged. | Check scripts that put `--home`, `--set`, `--yes`, `--non-interactive` or `--json` before the command name: they now do what they say. A `--yes` there now confirms. |
| **`upgrade` writes `dbPassword` into the target buildomatic's `default_master.properties`** from `database.passwordRef` when the file you prepared has none, and refuses before the service stops when neither exists (#339, ADR-0064). | Nothing, if `database.passwordRef` is set. Otherwise set it, or put `dbPassword` in the target's file yourself. |
| **A jrsctl home that is not a folder, or a run lock that cannot be taken, is exit 2** with the path and a remedy (#351). The lock case used to be exit 4 although nothing had run. | Nothing, unless a script treats exit 4 from these cases specially. |

No configuration key was removed or renamed. The one new key, `vendor.sourceJavaHome`, is optional; unset, upgrades behave as in 2.8.0.

## New

- **`runs abandon <id> [--yes] [--json]`** (#350, ADR-0066). It closes a pending run as it stands, for when the server was already put right another way (a restore, a redeploy, the remaining steps done by hand) or when compensating would undo a state that is now good.
  - It first lists the steps completed, interrupted, rolled back and never started, and warns when the run left the service stopped. Abandoning does not start the service.
  - It asks `[y/N]`; `--yes` answers. Nothing runs or is undone: the run is recorded as ended with exit 4, with an audit row naming who abandoned it and when.
  - `runs list` and `runs show` print `ABANDONED (exit 4)`; their JSON adds `"abandoned": true|false`. The exit-8 message and the guided menu ("Close job") offer it.
  - The run's backups stay until `jrsctl runs prune` removes them under `backups.retentionDays`.
- **`vendor.sourceJavaHome`** (#338, ADR-0065). When the installed version and the target share no Java (8.x supports 8 or 11, 10.x supports 17 or 21), set `vendor.javaHome` to the target's JDK and `vendor.sourceJavaHome` to the installed version's: `jrsctl config set vendor.sourceJavaHome <dir>`.
  - The point-B full export and `upgrade rollback --restore-database` run the old version's tools on it.
  - The upgrade refuses, before anything is stopped, a source JDK the installed version does not support, unless `--export` supplies the export (newdb only). A `--test` rehearsal does not judge it (#348).
  - `upgrade rollback --restore-database` refuses an unfit source JDK when it is planned, before the server is stopped (#348).
  - `doctor` reports `vendor-java` as WARN, not FAIL, when only `vendor.sourceJavaHome` fits the installed version: vendor-strategy `export`/`import` and `passwords` still use `vendor.javaHome`, so use the REST strategy for them until the upgrade is done.

## Fixed

- **Upgrades into a new Tomcat (`--tomcat-dir`)**
  - The service steps after the vendor run start, stop and wait for the new Tomcat, not the old one (#340, ADR-0062). The `manual` start instruction names the new Tomcat's `bin` directory. A rollback stops the new Tomcat and starts the old one.
  - On a WAR install, `point-config-at-target` also moves `server.installDir` to the new Tomcat (#343, ADR-0063). On the bundled layout the key is kept and the plan warns with the command to set it. `upgrade rollback` restores it with the rest of `config.yaml`.
  - The Windows service re-registration the plan prints for you to run gives `service.bat install` through `cmd /c` with `JAVA_HOME` and `CATALINA_HOME` set, and says the service reads no `setenv.bat` (#341). jrsctl still does not re-register the service itself.
- **Upgrade details** (#341). The plan fingerprint also covers `--tomcat-dir`, `--export`, `--key-alias`, `--key-password-ref` (as its reference) and `--migrate-passwords` when set. With `--export`, the rollback point names the adopted export. `runs show` lists an upgrade run's webapp and buildomatic archives and its full export under Backups.
- **A jrsctl home that is not a folder** (a file, a link to nothing) is refused by every command at start-up with one line and a `--home <dir>` / `JRSCTL_HOME` remedy, instead of an "unexpected" error with a stack trace and a logback status dump (#351).
- **Windows directory flushes** are no longer attempted, and no longer log an exception on every snapshot; NTFS journals the rename itself (#351).

## Documentation

- **Operator guide, spec §5.1, §5.5, §6.6, §7.4, §10.1 and §12, ADR-0062 to ADR-0066:** the changes above.
- **Recovery runbook:** `runs abandon` as the fourth choice for exit 8, and a new section for exit 2 when the home or the run lock is unusable.
- **README, `SECURITY.md`, `BUILD_STATUS.md`:** name 2.9.0 as the current release.

## Known limitations

- **The upgrade fixes are tested against fake vendor scripts only** (#338 to #341, #343, #348). The next 8.x → 10.x run with `--tomcat-dir` on a real installation is their live check. Run `upgrade --plan` and `upgrade --test` first.
- **`runs abandon` does not check that the server is right.** It records the operator's decision; the preview and the audit row show it afterwards.
- **Vendor-strategy `export`, `import` and `passwords` use `vendor.javaHome` only**, not `vendor.sourceJavaHome`.
- **As in 2.8.0:**
  - `jobs record`, `pause` and `resume`, and the job states in the sidecar, are tested against a mocked server only;
  - `customizations scan --target-vendor` is verified against fixture webapps only, and `customizations readiness` has not been run against a real 8.2 site;
  - `import verify --content` has been run against one 10.0.0 PRO server only;
  - the JUnit file of `--junit` has been checked with the JDK's XML parser only;
  - `repository load` has run against a live server on one machine only, and supports PostgreSQL and MySQL only;
  - `passwords migrate` has never run against a live server;
  - jrsctl does not move a Windows service or systemd unit to a new Tomcat;
  - a buildomatic on a network share (#31), the adapter against live servers other than 10.0.0 PRO (#35), Windows containers not detected, `logs/jrsctl.log` not rotated, and the pager in unusual consoles.
