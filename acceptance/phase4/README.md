# Phase 4 acceptance — Export / Import

Run: `scripts\mvn.cmd verify -Dphase=4`.

Criteria (spec §14, Phase 4). Unit suites in `ops` (`DefaultExportImportOperationsTest`, `ExportRunTest`, `ImportRollbackTest`) and `app` (`ExportCommandTest`, `ImportCommandTest`) cover the detail: strategy selection with the reason in the summary, the precheck / backup / import phase composition, the REST export executed by the real `Runner` against WireMock, and the failed import that re-imports the pre-import snapshot with `update` and exits 3. `Phase4ExportImportTest` proves the packaged jar end to end against a WireMock JasperReports Server 8.2.0 PRO (`network.mode: public`, `service.kind: manual`) whose async endpoints answer at once. Its steps share one home and one archive and therefore run in order:

1. `jrsctl export --uri /public --out <tmp>/x.zip --yes` exits 0; `x.zip` (1 MB from `GET /rest_v2/export/e1/export.zip`) and `x.zip.jrsctl.json` exist, and the sidecar carries `serverVersion` 8.2.0, `strategy` REST and the exported uri. WireMock saw one `POST /rest_v2/export`.
2. `jrsctl import <tmp>/x.zip --update --plan` exits 0 and prints the phases `precheck`, `backup` (with the `Pre-import snapshot` step) and `import` (with `Enable snapshot rollback`), the warning `Rollback re-imports the pre-import snapshot; it restores overwritten resources but cannot delete resources the failed import created.` and `nothing has changed`; no further request reached the server.
3. `jrsctl import <tmp>/x.zip --update --yes` exits 0; WireMock saw a second `POST /rest_v2/export` (the pre-import snapshot, stored under `<home>/snapshots/pre-import/`) and exactly one `POST /rest_v2/import`; `runs list --json` shows a `SUCCEEDED` `import` run.
4. A copy of the archive whose sidecar carries a different `keystoreFingerprint` is refused: `import y.zip --yes` exits 2 with `keystore fingerprint mismatch` and the `--source-keystore` remediation, and neither a snapshot nor an import request was made. The keystore comparison (`CheckKeystoreFingerprint` in `jrs`) only fails when the target server's fingerprint is *known*; with no keystore it warns and continues. The fake server has no keystore, so the test starts the jar with `JAVA_TOOL_OPTIONS=-Duser.home=<tmp>/userhome` holding a `.jrsks`: with `server.runAsUser` unset the inspector reads the current user's home, which makes the target fingerprint known and different.

Not covered here (release gates or later phases): the vendor CLI strategy end to end (`js-export`/`js-import` with a stopped service; unit-tested in `jrs` and composed in `ops`), `--source-keystore` import of a foreign keystore (needs buildomatic), a real failed import through the jar (the fake server always reports `ready`; the rollback path is proven by `ImportRollbackTest`), Ctrl-C cancellation (Phase 8).
