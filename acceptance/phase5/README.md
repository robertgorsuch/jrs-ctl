# Phase 5 acceptance — Upgrade

Run: `scripts\mvn.cmd verify -Dphase=5`.

Criteria (spec §14, Phase 5; contract in spec §10). Unit suites in `ops` cover the detail (`UpgradePlanTest` for the phases, step ids, the `samedb` gate, the compat-matrix path and vendor-Java checks; `UpgradeRunTest` for the whole plan through the real `Runner` with a fake `js-ant` executed by the real process runner, the smoke-failure rollback to point B and the rollback plan; `HotfixReconcilerTest` for REAPPLICABLE/SUPERSEDED; `CustomizationReapplyTest` for the 3-way reconcile; `CustomizationOperationsTest`, `UnifiedDiffTest`, `ArchivesTest`). `Phase5UpgradeTest` proves the packaged jar end to end against:

- a fake Tomcat layout (`jasperserver-pro` webapp, `conf/Catalina/localhost/*.xml`, `buildomatic/` with `js-export` writing a fake archive and `default_master.properties` carrying a password that must never be copied);
- a fake target package (`buildomatic/js-ant` copies `webapp-new/` over the webapp and honours `JAVA_HOME`; `jasperserver-pro/` webapp directory);
- a fake `catalina` script (`service.kind: catalina`) whose *running* state the real script service controller can observe: on Windows it starts a copy of `ping.exe` named `tomcat9.exe` under `<tomcat>/bin` (the process finder recognises the Tomcat service wrapper name and its home), on Linux a `sh -c 'sleep 900 # -Dcatalina.base=<tomcat>'`; `stop` kills it. A script that merely exits 0 is not enough, because start/stop wait for a Tomcat process to appear or vanish;
- a WireMock JasperReports Server 8.2.0 PRO that also answers the smoke test (`/rest_v2/resources`, `/jobs`, `/export` start/state/download). It keeps reporting 8.2.0 after the "upgrade"; assertions are on the plan and on file effects, never on the reported version;
- a fake user home (`JAVA_TOOL_OPTIONS=-Duser.home=<tmp>`) holding `.jrsks`/`.jrsksp` so `doctor`'s keystore check and the keystore backup have something to inspect.

The vendor JDK: `verify-target-package` requires `vendor.javaHome` to be the Java major the compat matrix lists for the target (Java 17 for 9.x, 11 for 8.x). On Linux the test writes a shell-script `java` that prints a 17 banner and targets 9.0.0. On Windows a script cannot stand in for `java.exe`, so the test looks for a real JDK (`JRSCTL_VENDOR_JDK`, `JAVA_HOME_17_X64`, `JAVA_HOME_11_X64`, then `C:\Program Files\{Java,Microsoft,Eclipse Adoptium,Amazon Corretto,Zulu}\*jdk*` and `C:\*jdk*`); a JDK 17 targets 9.0.0, a JDK 11 targets 8.3.0 (8.x -> 8.x is a supported path), neither aborts the test with an assumption message. The steps share one home and run in order:

1. `jrsctl upgrade --to <target> --package <pkg> --plan` exits 0 and prints the five phases `preflight`, `backup`, `vendor-upgrade`, `reconcile`, `verify`, the newdb line ("complete file and connection restore") and "nothing has changed"; the webapp is untouched.
2. `--mode samedb --plan` without `--db-backup-confirmed` exits 2 and prints the gate message naming the flag; with the flag the plan carries `confirm-db-backup` and the spec §10.1 sentence "Rollback restores files only. Restore the database from your own backup before running rollback."
3. `upgrade ... --yes` exits 0: doctor passed (its `runs`/`lock` findings about the run itself and `vendor-java` judged against the old version are tolerated), the full export ran, keystore/webapp/buildomatic/config were backed up under `snapshots/<runId>/` (`full-export.zip`, `backup-webapp/webapp.zip|tar.gz`, `backup-config/`, `backup-keystore/`, `upgrade.json`), the service was stopped and started around the vendor script, the webapp now holds `upgraded.marker` and the new `version.txt`, the target package's `default_master.properties` carries the copied database settings but not `dbPassword`, `runs list --json` shows a `SUCCEEDED` `upgrade` run and `runs show` lists `run-vendor-upgrade`.
4. `upgrade rollback <runId> --to-point B --plan` prints `restore-webapp` and the files-only warning; `--yes` exits 0 and the marker is gone, the old `version.txt` and `x.jar` are back.
5. `customizations register|list|diff|unregister` round-trip a file under the webapp: `diff` exits 0 while unchanged, 1 with `-b=2`/`+b=3` after an edit; a file outside the installation is refused with exit 2.

Not covered here (release gates or later phases): a real vendor script (`js-upgrade-newdb`/`upgrade-newdb` target names are unverified against a real buildomatic), hotfix re-application through `--reapply-hotfixes` (unit-tested classification only; the embedded apply plan needs a real bundle), Ctrl-C cancellation (Phase 8).
